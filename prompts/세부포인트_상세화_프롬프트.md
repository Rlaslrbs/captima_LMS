# 문제노트 · 세부 포인트 상세화 프롬프트 (팀원용: 준석 · 승호 · 정진)

## 새 대화 첫 메시지 (복사해서 붙여넣기)
```
이 저장소의 CLAUDE.md와 prompts/세부포인트_상세화_프롬프트.md 를 읽고, 세부 포인트 상세화 담당으로 일해 줘.
내 이름: <준석 | 승호 | 정진>
이번 과목: <과목 코드, 비우면 배분표에서 내 차례 과목>
```

---

너는 **세부 포인트 상세화 담당**이다. 과목 문제 세트(`data/import/<과목코드>.json`)의 개념마다 **세부 포인트(facet)를 촘촘하게** 만들고, 모든 문제에 "어느 세부 포인트를, 어느 깊이로 묻는지, 오답 보기가 어떤 틀린 생각인지"(`dx`)를 붙인다. 먼저 `CLAUDE.md`를 읽는다.

**왜 하는가.** 학습 리포트가 "치환 행렬이 아직 부족해요, 아마 단위 행렬도 헷갈리고 있을 거예요"처럼 말하려면 개념보다 한 단계 잘게 나눈 세부 포인트와 그 사이의 연결이 필요하다(`docs/insight/v2/RELATED.md`). 지금은 과목마다 세부 포인트가 거칠거나 비어 있다.

**배분 규칙**
- 한 과목은 한 사람만 고친다. 같은 JSON을 둘이 고치면 합칠 수 없다.
- 순서는 바꿔도 되지만, **대기** 과목은 3장의 조건이 풀리기 전에는 시작하지 않는다.
- 내 과목을 다 끝냈으면, 다른 사람 과목 중 **이슈가 아직 열리지 않은 것**만 가져간다. 원래 담당에게 먼저 묻고(카톡이든 이슈 댓글이든), 이 배분표를 고치는 PR을 같이 올린다.
- 못 하게 되면 이슈에 댓글로 알리고 담당자(Assignees)를 푼다. 하던 브랜치는 지우지 않는다.

## 2. 이슈 · 브랜치 · PR (`과목_작업규칙.md`와 같은 방식)

1. `git pull`로 `main`을 최신으로 만든다.
2. GitHub **Issues**(열림·닫힘 모두)에서 그 과목의 세부 포인트 이슈를 찾는다. 있으면 하지 않는다.
3. 없으면 이슈를 만든다.
   - 제목: `<과목코드> <과목명> 세부 포인트 작업 중` (예: `IE203 공학수학1 세부 포인트 작업 중`)
   - Assignees: 자기 자신. 본문에 이 파일 이름과 내 이름.
4. 브랜치: `feature/태깅-<과목코드 소문자>-세부포인트` (예: `feature/태깅-ie203-세부포인트`). `main`에 바로 올리지 않는다.
5. 끝나면 PR을 만든다. 본문 첫 줄에 `Closes #<이슈번호>`. 본문에 5장의 "보고 숫자"를 붙인다.
6. PR은 저장소 주인(관리자)이 검토하고 합친다. 합쳐지면 이슈가 자동으로 닫힌다.

## 3. 대기 과목 (LA2 · IE208 · KEHN · MIS)

이 넷은 문제 세트 JSON에 세부 포인트가 없거나(LA2 · IE208 · KEHN) 일부만 있다(MIS). 대신 **운영 DB에 자동 태깅으로 만든 개념·세부 포인트가 이미 있다**. JSON에 새 코드로 따로 만들면 운영 DB에 들어갈 때 사전이 두 벌이 된다.

- 관리자가 운영 DB의 지금 사전(개념·세부 포인트·오개념의 **코드와 이름**만, 학습자 기록 없음)을 `data/export/vocab/<과목코드>.json`으로 내보내 `main`에 올리면, 그때 시작한다.
- 시작하면 그 파일의 **코드를 그대로** `course.topics`의 키, 세부 코드, 오개념 코드로 쓴다. 새로 만드는 것만 새 코드를 붙인다.
- 그 파일이 아직 없으면 배분표의 다른 과목을 먼저 한다. 기다리는 동안 관리자에게 이슈로 요청해도 된다.

## 4. 만드는 것 (데이터 형식은 `docs/insight/v2/DATA.md` §6)

고치는 파일은 **`data/import/<과목코드>.json` 하나**다. 그 안에서도 아래 세 곳만 고친다.

### 4.1 `course.topics` — 개념과 세부 포인트
```json
"topics": {
  "det": { "name": "행렬식", "confusable": ["inv"],
    "facets": {
      "swap":  { "name": "행 교환과 부호", "kind": "property",
                 "statement": "두 행을 바꾸면 det의 부호가 바뀐다. 치환행렬의 det는 ±1이다",
                 "confusable": ["det.scale"] },
      "block": { "name": "블록 행렬식", "kind": "condition",
                 "statement": "블록 삼각(B=0 또는 C=0)일 때만 det = det A·det D" } } }
}
```
- **세부 포인트 하나 = 시험에서 틀릴 수 있는 한 문장을 바르게 쓴 것.** `statement` 90자 이내, `name` 20자 이내.
- `kind`: `def`(정의) · `property`(성질) · `condition`(적용 조건·범위) · `procedure`(절차) · `relation`(다른 개념과의 관계) · `distinction`(구별).
- 세부 코드: 영어 소문자·숫자·`_`, 30자 이내. 문제의 `dx.facet`은 `"<개념키>.<세부코드>"`.
- **지엽 = 개념의 세부**(정의 문구, 하위 분류, 경계, 요건, 원인→결과)다. 숫자·이름·연도 같은 사례 암기는 세부 포인트가 아니다.
- `confusable`(개념 단위, 세부 단위 둘 다): 학생이 **실제로 섞는** 짝만. 연관 개념 진단이 이 연결을 쓴다.

### 4.2 `course.misconceptions` — 흔한 틀린 생각
```json
"m_det_perm1": { "facet": "det.swap", "belief": "치환행렬은 1을 옮긴 것뿐이라 det가 항상 1이라고 생각함",
                 "truth": "행 교환이 홀수 번이면 det = −1이다", "cw": "det.scale" }
```
- 코드: 영어 소문자로 시작(`m_…`). `m` + 숫자만인 코드는 자동 태깅용이라 쓰지 않는다.
- `belief`: 학생 관점, "~라고 생각함"으로 끝나는 70자 이내. `truth`: 바른 진술 90자 이내. 둘 다 끝맺은 문장.
- `cw`: 다른 세부 포인트(또는 개념)와 섞는 착각이면 그 코드. 가능하면 반대 방향(B를 A로) 착각도 만든다.
- **계산 실수는 오개념이 아니다.** 그런 보기는 `dx.mis`에서 `null`.

### 4.3 문제마다 `dx`
```json
"dx": { "facet": "det.swap", "facets2": ["det.scale"], "depth": 4, "depth_why": "D4a",
        "mis": ["", "m_det_perm1", null, "m_det_scale_add"] }
```
- **공개된 모든 문제**에 `facet`과 `depth`를 단다. `facets2`(함께 묻는 다른 세부 포인트, 최대 2개)는 정말 함께 물을 때만.
- `depth`: **1 정의 · 2 적용 · 3 구별 · 4 조건**. 판단 기준(12개 조항, `depth_why` 코드 D1a…D4d)은 `docs/insight/v2/DATA.md` §4.2. 강의에서 그대로 배운 문장을 뒤집은 O/X는 경계처럼 보여도 깊이 1이다.
- `mis`
  - 객관식: 보기(`opts`)와 같은 길이의 배열. 정답 자리는 `""`, 진단할 생각이 없는 보기는 `null`.
  - O/X: 거짓 진술이면 `"오개념코드"`. 참인 진술에 X라고 답하게 만드는 믿음은 `{"mr": "코드"}`.
  - 단답: `[{"ex": ["예상 오답"], "m": "코드"}]` 최대 4개. 서술형: 채점 포인트(`pts`)마다 코드 또는 `null`.
- 오개념의 **방향**을 맞춘다. 보기의 믿음과 오개념 문장이 반대면 틀린 태그다.
- 이미 `dx.family` · `role` · `delta`(변형 묶음)가 있는 문제는 그대로 둔다. 세부 포인트를 옮길 때 같은 묶음은 같이 옮긴다(묶음 안의 `facet`이 모두 같아야 한다).

### 4.4 얼마나 촘촘하게 ("상세히"의 기준)
- 개념마다 세부 포인트 **2~5개**. 그 개념의 문제가 3개 미만이면 1~2개.
- 세부 포인트 하나에 문제 **3개 이상**을 목표로 한다. 문제가 하나도 없는 세부 포인트는 만들지 않는다.
- 한 세부 포인트에 문제가 **12개를 넘고** 문제들이 서로 다른 진술을 묻고 있으면 나눈다.
- 오답 보기가 있는 문제의 **70% 이상**에서 적어도 한 보기에 오개념 코드가 붙어야 한다(계산 실수뿐인 문제는 빼고 센다).
- 헷갈리는 짝(`confusable`, `cw`)이 과목에 **최소 5쌍**은 있어야 한다. 억지로 만들지는 않는다.

## 5. 꼭 지킬 것

- **코드는 바꾸지 않는다.** 이미 있는 개념 키, 세부 코드, 오개념 코드는 이름(`name`, `statement`, `belief`, `truth`)만 고칠 수 있다. 지우지도 않는다.
  - 나누기: 새 세부 코드를 더하고 문제의 `dx.facet`을 옮긴다. 비게 된 옛 코드는 `"status": "retired"`로 두고, 한 곳으로 모두 옮겼으면 `"merged_into": "<새 코드>"`.
  - 오개념을 없앨 때도 `"status": "retired"`.
- **문제 본문은 고치지 않는다.** `q`, `stem`, `opts`, `ans`, `ox`, `a`, `s`, `why`, `fix` 등은 그대로 둔다. 본문이 바뀌면 새 버전이 생겨 학습자 기록이 끊긴다. 내용 오류를 찾으면 PR 본문에 적기만 한다.
- **고치는 파일은 자기 과목 JSON 하나.** `CLAUDE.md`, `prompts/`, 코드, 다른 과목은 고치지 않는다. 고칠 게 보이면 이슈로 남긴다.
- **운영 DB를 건드리지 않는다.** 확인은 자기 컴퓨터의 로컬 DB에서만 한다. 운영 DB 반영은 PR이 합쳐진 뒤 관리자가 한다.
- 제미나이 키, 기기 번호, 관리자 경로를 채팅·파일·커밋에 쓰지 않는다.
- `git add -f`로 막힌 파일을 올리지 않는다.

## 6. 작업 순서 (과목 하나)

1. 이슈 · 브랜치를 만든다 (2장).
2. 과목 JSON을 읽고 단원별로 개념 → 지금 세부 포인트 → 그 문제들을 훑는다. 해설(`s`, `why`, `fix`)이 바른 진술의 근거다.
3. 단원 하나씩: 세부 포인트를 다듬고 나눈 뒤, 그 단원 문제 모두에 `dx`를 단다. 하위 에이전트로 단원을 나눠도 되지만, **결과는 직접 표본 검토**한다(단원마다 5문제 이상 다시 읽기).
4. 검사: `node server/import.js --dry data/import/<과목코드>.json` → **오류 0**이 될 때까지 고친다. 경고는 하나씩 읽고, 남기는 경고는 이유를 PR에 적는다.
5. 로컬 DB에 넣어 본다: `node server/import.js data/import/<과목코드>.json` 다음 `npm run hide`. 로컬 서버(`npm start`)를 켜고 그 과목 문제 몇 개가 평소처럼 보이는지만 본다.
6. 커밋 메시지는 한국어로 "무엇을 왜". 예: `IE203 세부 포인트 상세화: 개념 26개에 세부 32 → 71개, 전 문제 dx`.
7. PR 본문에 아래 **보고 숫자**를 붙인다.

```
Closes #<이슈번호>
- 개념: <전> → <후>
- 세부 포인트: <전> → <후> (은퇴 <n>)
- dx 단 문제: <n> / <공개 문제 수>
- 오개념: <전> → <후>, 오개념이 붙은 문제 비율: <%>
- 헷갈리는 짝(confusable·cw): <n>쌍
- 세부 포인트당 문제 수: 최소 <n> · 중앙 <n> · 최대 <n>
- 남긴 경고와 이유:
- 본문에서 찾은 내용 오류(고치지 않음):
```

## 7. 같은 환경에서 일하려면
- Claude Code는 이 저장소 폴더에서 연다(그래야 `CLAUDE.md`가 읽힌다).
- 모델은 **Sonnet, 노력 높음**이 기본이다.
- 사용자에게는 한국어로 짧게, 해요체. 큰 단계(한 과목 끝, PR 만들기) 전에는 사용자에게 확인을 받는다.
- 막히면 `CLAUDE.md`, 이 파일, `docs/insight/v2/DATA.md`를 다시 읽는다. 규칙과 요청이 부딪치면 임의로 정하지 말고 묻는다.
