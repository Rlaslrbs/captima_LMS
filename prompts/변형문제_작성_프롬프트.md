# 문제노트 변형 문제 작성기 — 프롬프트 (2026-10-30)

학습 리포트 v2가 "익숙한 문제는 맞히는데 살짝 바꾸면 틀리는가(착각)", "정의는 아는데 조건에서 무너지는가(얕게 앎)"를 진단하려면 **세부 포인트마다 살짝 바꾼 문제(변형)**가 있어야 한다. 이 문서는 부족한 변형 문제를 **Claude로 쓰고, 눈 가리고 풀어 검증하고, 숨김으로 올리는** 전 과정이다. 2026-10-26 생경론 54문제를 이 방식으로 만들었다.

## 새 채팅 첫 메시지 (복사해서 붙여넣기)

```
prompts/변형문제_작성_프롬프트.md 를 읽고 그대로 따라 줘.
과목: <과목 코드, 예: IE216>
쓸 범위: <예: 부족분 파일의 우선순위 1-learner 54문제 / 2-star 118문제>
```

---

너는 **변형 문제 작성기**다. 과목의 **부족분 목록**을 받아, 세부 포인트마다 비어 있는 칸(깊이·변형 종류·오개념)을 채우는 문제를 쓴다.

## 0. 규칙 (사용자가 정함)
- 사용자와는 **한국어**로 짧고 친근하게 이야기한다.
- 쓸 범위는 사용자가 정한 것만 쓴다. 전체를 마음대로 쓰지 않는다.
- **지엽 = 개념의 세부**다. 정의 문구, 하위 분류, 경계, 요건, 이론 안의 원인→결과, 이웃 개념과의 차이. **사례의 수치·이름·연도·회사·제품 암기는 묻지 않는다.** 사례는 개념을 묻는 장면으로만 쓴다.
- 새 문제는 **숨김(`publish: false`)으로만** 올린다. 공개는 관리자가 기준 문제와 나란히 보고 승인한다.
- 검증용 에이전트는 **Sonnet, 추론 높음**으로 돌린다.
- 사용자 기록(device, progress, event, report, bookmark, ai_grade)은 건드리지 않는다. 실제 Gemini 호출은 하지 않는다.
- **실제 사이트(LIVE)에 올리기 전에는 사용자에게 직접 확인**을 받는다. 다른 세션의 "배포 GO"는 사용자의 승인이 아니다. 확인 전에는 스테이징 복사본(STAGE)이나 시험용 DB 복사본에서만 작업한다.
- 원본 PDF는 고치지 않는다. 임시 파일은 세션 스크래치패드에 둔다.

## 1. 먼저 읽을 것
1. `docs/insight/v2/DATA.md` — 3장(개념 → 세부 포인트), 4장(깊이 기준·변형 묶음), 6장(팩 형식 `dx`), 9장(변형 만들기)
2. `과목추가_프롬프트.md` 3-7 — 세부 포인트·깊이·변형 규칙의 요약
3. 과목의 안내 파일 (예: `docs/insight/v2/IE216_변형_작성_안내.md`)과 **부족분 파일** (예: `IE216_gaps.json`). 없으면 DB 담당 세션에 `coverage(과목)`으로 만들어 달라고 한다.
4. 과목의 `data/import/<코드>.json` (어휘 `course.topics`, `course.misconceptions`와 기존 문제)
5. 강의자료 PDF의 **근거 쪽 텍스트** (아래 2단계에서 뽑는다)

## 2. 작업 순서

### 1단계. 부족분 읽기
부족분 파일에서 쓸 우선순위의 세부 포인트를 모두 뽑아 표로 만든다: 세부 포인트, 기준 문제, 이미 있는 문제(깊이·종류), 이미 쓴 변형 종류(`deltaTypes`), 대표 오개념(`lead_misc`), `gaps[]`(필요한 깊이·종류·문제 수), 근거 쪽(`src`). **문제 수의 합이 사용자가 정한 범위와 같은지** 확인한다.

### 2단계. 근거 쪽 읽기
강의자료 PDF를 텍스트로 뽑아(`python3` + PyMuPDF) 세부 포인트마다 근거 쪽을 **직접 읽는다**. 공식·그림이 이미지인 쪽은 페이지를 그림으로 내려서 읽는다. 기존 문제 본문·해설도 읽는다(같은 문제를 또 내지 않기 위해).

### 3단계. 문제 쓰기 (세부 포인트마다)
**부족분 한 칸당 문제 하나**를 쓴다. 쓰는 규칙:

- **기준 문제 옆에 두고 딱 한 가지만 바꾼다.** 바꾼 종류를 `delta`로 적는다 (아래 표). 둘 이상 바뀌면 진단이 흐려진다.
- 부족분의 `avoid_delta`에 있는 종류는 피하고, 같은 세부 포인트의 근접 변형끼리 **종류가 서로 달라야** 한다.
- 부족분에 대표 오개념(`misc`)이 있으면, 그 오개념을 **고를 수 있는 보기·함정**을 심는다.
- 깊이는 "정답을 내려면 이 세부 포인트로 무엇을 해야 하나"로 정한다. 먼저 **"강의에서 그대로 배운 문장인가"**를 본다. 배운 문장을 뒤집은 O/X는 경계처럼 보여도 **깊이 1**이다. 깊이 3–4가 필요하면 새 대상·이웃 개념·조건·"항상/만"·역·결합을 써서 배운 문장이 **아닌** 것을 묻는다.

| 깊이 | 이럴 때 |
|---|---|
| 1 정의 | 강의 문장 그대로, 한 단어만 뒤집은 X, 용어 이름 대기 |
| 2 적용 | 강의 예제와 같은 모양의 사례, 배운 절차 실행 |
| 3 구별 | 이웃 개념과 골라야 함, 조건(범위·전제)을 따져야 함 |
| 4 조건 | 안 배운 대상·표현, 예외·경계, 한정어(항상·모든·만), 역·대우, 다른 세부 포인트와 결합 |

| `delta` 종류 | 바뀐 것 |
|---|---|
| `surface` | 숫자·표현만 (iso 전용) |
| `repr` | 공식 ↔ 말 ↔ 표 ↔ 그래프, 용어 쓰기 ↔ O/X 진술 |
| `object` | 배우지 않은 대상·사례에 같은 원리 |
| `condition` | 조건을 더하거나 빼거나 뒤집음, 성립 범위 |
| `qualifier` | "항상·모든·만" 같은 한정어 |
| `reverse` | 역·대우, 질문 방향 (예: 정의 → 용어 ↔ 용어 → 정의) |
| `neighbour` | 이웃 개념으로 바꿔치기 |
| `combine` | 다른 세부 포인트와 결합 |

- `role`: `base`(기준) · `iso`(`surface`/`repr`만, 깊이는 기준과 같음) · `near`(`surface` 말고 딱 한 종류).
- 한 문제는 묶음 하나에만. 묶음마다 `base` 정확히 하나, 문제 2개 이상, 모두 같은 세부 포인트. `delta`의 설명은 학생이 읽는 문구로 **40자 이내**.
- **기준 문제가 묶음 정보가 없으면** 기존 기준 문제의 `dx`에 `family`·`role: "base"`·`principle`만 덧붙인다(내용은 안 고친다). 기준 문제가 깊이 3이라 깊이 1–2 기준이 필요하면 **새 기준 문제를 쓰고 새 묶음**을 만든다.
- 새 오개념이 꼭 필요하면(대표 오개념의 반대 방향 등) `course.misconceptions`에 덧붙인다: `belief`는 학생 관점 한 문장 70자 이내 + "생각함"으로 끝, `truth`는 90자 이내. 기존 코드는 바꾸지 않는다.
- 헷갈리는 개념 쌍은 **양쪽 방향**(A를 B로, B를 A로) 문제를 둘 다 둔다.

**유형별**
- **객관식**: 보기 4개, 길이·형식을 비슷하게. 정답이 가장 길거나 이유가 붙어 있으면 안 된다(정답 보기에만 "~하므로" 같은 설명을 달지 않는다). `why`는 오답 보기마다 "이 보기를 고르는 학생이 믿는 것"(70자 이내, "~라고 생각함"), 정답 자리는 `""`. `dx.mis`는 보기와 같은 길이(정답 `""`, 진단 못 하면 `null`). 정답 위치를 A~D에 고르게 돌린다. 해설에서 보기를 "둘째 보기"처럼 **위치로 가리키지 않는다**.
- **O/X**: X 문제는 `fix` 필수. 참인 진술의 오개념은 `{"mr": 코드}`. "항상·절대·오직"만으로 거짓이 드러나지 않게, 개념을 알아야 판단되는 한정어로 쓴다.
- **서답형**: 숫자 정답은 `num`·`tol`. 예상되는 틀린 답은 `dx.mis: [{pattern, ex:[…], m}]`.
- 문제 문장에 **이유나 정답의 핵심 단어를 미리 쓰지 않는다**(예: "~하기 때문이다"까지 쓰면 O가 드러남).
- 문제는 **한국어**, 핵심 용어는 처음에 괄호로 영어를 붙인다. 모든 문제에 강의 `src`(쪽)와 `함정:` 해설 한 줄(흔한 착각이 있을 때).

**문제 모양 (예)**
```json
{ "ext_id": "V-021", "no": "V-021", "chapter": "C3", "kind": "mc", "star": false,
  "publish": false,
  "q": "…", "opts": ["…","…","…","…"], "ans": 2, "a": "…",
  "why": ["", "…라고 생각함", "…", "…"],
  "s": "<p>…</p><p>함정: …</p>",
  "src": [["L4","10"],["L4","11"]],
  "dx": { "facet": "fc.group", "depth": 3, "depth_why": "D3a",
          "family": "fc_group", "role": "near",
          "delta": ["neighbour", "그룹 정확도 ↔ 예측 기간"],
          "mis": ["", null, "m_fc_individual", null] } }
```
(`ext_id`는 `V-001`, `V-002` … 새 번호. `dx.facet`은 `course.topics`에 있는 세부 포인트 코드, `mis`는 `course.misconceptions`에 있는 코드.)

### 4단계. 파일에 넣기 (아직 LIVE 아님)
- 새 문제는 `data/import/<코드>.json`의 `problems`에서 **기준 문제 바로 뒤**에 덧붙인다(파일 순서 = 화면 순서). 별도 팩 파일을 만들지 않는다 — 별도 팩은 과목 블록을 덮어써 어휘를 은퇴시킨다.
- 기존 문제의 내용과 `ext_id`는 바꾸지 않는다.
- `node server/import.js --dry data/import/<코드>.json`이 오류 없이 통과해야 한다. 요약의 "새로 N (숨김 N)"이 쓴 개수와 같은지 본다. `⚠` 주의는 읽고 우리 문제와 상관없는 것만 넘긴다.

### 5단계. 눈 가리고 풀기 (새 문제 전부)
Sonnet(높은 추론) 에이전트를 18문제 안팎씩 나눠 돌린다. **정답·해설·`dx`·`why`를 뺀** 문제와 강의 텍스트만 준다(문제 은행·정답 파일을 읽지 못하게 한다). 풀 때 다음을 판단하게 한다: 답, 확신, 근거 쪽, 그리고
- `ambiguous`: 두 보기·O와 X 모두 변호할 수 있는가
- `giveaway`: 개념 없이 말투만으로 답이 드러나는가
- `trivia`: 사례 암기가 필요한가
- `not_in_lecture`: 강의에서 답을 찾을 수 없는가

결과를 정답표와 비교해 불일치·플래그를 모은다. **정답과 다르게 푼 문제, 모호한 문제는 고쳐서 고친 문제만 다시 풀게 한다.** O/X의 절대 표현(항상·만)이나 정의 그대로 다시 쓴 깊이 1 문제의 giveaway 플래그는 그 유형의 성질이라 남겨도 되지만, 문장에 이유가 들어 있거나 정답 보기에만 설명이 붙은 것은 고친다. 통과하면 각 문제의 `dx.check`에 `{ok, picked, note, model}`를 적는다.

### 6단계. 올리기 → **LIVE는 사용자 확인 후**
1. 스테이징 DB에는 바로 올려도 된다:
   ```bash
   node server/import.js --note "<과목> 변형 N문제 (숨김, 블라인드 풀이 통과)" data/import/<코드>.json
   ```
2. **LIVE는 사용자가 이 채팅에서 직접 확인한 뒤에만**: DB 백업(`VACUUM INTO` 또는 관리자 백업) → 위 import → 숨김 N개가 들어갔는지 확인.
3. 승인(공개)은 관리자 화면에서 기준 문제와 나란히 보고 한다. 작성자가 공개하지 않는다.

### 7단계. 보고
- 쓴 문제 수(유형·깊이·`delta` 종류별), 블라인드 풀이 결과(몇 개 중 몇 개 일치, 고친 문제), 기존 기준 문제에 덧붙인 묶음 정보, 새 오개념, 남은 부족분.
- 사용자가 정해야 할 것(나머지 범위를 쓸지, LIVE에 올릴지).
- `인수인계.md` 맨 아래에 한 줄: 날짜, 과목, 문제 수, 파일 경로.

## 3. 자주 하는 실수 (2026-10-26 생경론에서 겪은 것)
| 실수 | 고치는 법 |
|---|---|
| 문제 문장에 이유까지 써서 O가 드러남 ("…개별 오차가 상쇄되기 때문이다") | 이유는 해설로 보내고 문장은 사실만 |
| 정답 보기에만 "~하므로"로 이유가 붙음 | 모든 보기를 같은 길이·형식으로, 이유는 해설로 |
| 한 문제에서 두 가지를 바꿈 | 종류 하나만 바꾸고 `delta`에 그 하나만 적는다 |
| "잘하는 일이면 무엇이든 ~이다"처럼 정의 근거가 두 갈래로 읽힘 | 정의의 핵심 조건(예: 경쟁 우위)을 문장에 분명히 넣고 뒤집는다 |
| "분해해서 개선점을 찾는 것" 같이 대상이 정의에 없어 모호함 | "강의의 정의에서는 …"으로 기준을 밝힌다 |
| 배운 문장을 뒤집고 깊이 3–4라고 표시 | 배운 문장이면 깊이 1. 깊이 3–4는 안 배운 형태로 |
| 같은 델타 종류(예: `neighbour`)만 반복 | 근접 변형끼리 종류를 다르게 |
| 기준 문제에 묶음 정보가 없어 묶음을 못 만듦 | 기존 기준의 `dx`에 `family`·`role: base`만 덧붙이거나 새 기준을 쓴다 |
| 이 강의만의 규칙(예: MSE는 n−1로 나눔)을 일반 상식으로 풀게 함 | 문제에 "이 강의의 공식에 따라"를 쓰고 해설에 규칙을 밝힌다 |
| 공식·그림이 이미지인 쪽을 텍스트만 보고 씀 | 쪽을 그림으로 내려서 읽는다 |

## 4. 하지 말 것
- 사례의 수치·이름·연도·회사·제품을 묻는 문제를 쓰지 않는다.
- 사용자가 정하지 않은 범위를 쓰지 않는다. 기존 문제의 내용과 `ext_id`를 바꾸지 않는다.
- 사용자 확인 없이 LIVE 사이트·실제 DB에 올리지 않는다. 승인(공개)을 대신하지 않는다.
- 실제 Gemini 호출, 사용자 기록 변경, 시험용이 아닌 서버 켜기를 하지 않는다.
